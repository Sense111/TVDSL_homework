# HW5: отчёт

Инструмент: NuSMV 2.6.0 (основной). Spin не использовался, A/B со Spin нет; вместо него сравниваются режимы NuSMV (BDD и BMC/SAT).

## Модель

`peterson.smv`: два процесса, у каждого `pc ∈ {idle, want, wait, crit}`, общие `want0`, `want1 : boolean`, `turn : 0..1`. Шаг делает один процесс; кого именно, выбирает недетерминированно переменная `run : 0..1` (interleaving).

- `idle -> idle | want` (может захотеть, а может нет), при переходе в `want` поднимается `want_i`.
- `want -> wait`, при этом `turn := 1-i` (уступает очередь).
- `wait -> crit`, если `!want_j | turn = i`, иначе остаётся в `wait`.
- `crit -> idle`, `want_i := FALSE`.

Параметры: 2 процесса, 4 состояния, `turn ∈ {0,1}`. Кодировка занимает 8 булевых бит, то есть 256 комбинаций. **Достижимых из `init` состояний 40**, диаметр 7 (`compute_reachable` и `print_reachable_states -v`, `logs/reachable.log`).

## Свойства и результаты

| # | Описание | Формула | Результат |
|---|---|---|---|
| S1 | Взаимное исключение | `G !(crit0 & crit1)` | true |
| S2 | Флаг процесса 0 поднят, пока он в критической секции | `AG (crit0 -> want0)` | true |
| S3 | Флаг процесса 1 поднят, пока он в критической секции | `AG (crit1 -> want1)` | true |
| L1 | Каждый запрос процесса 0 в итоге приводит к входу | `G (trying0 -> F crit0)` | **false** |
| L2 | Каждый запрос процесса 1 в итоге приводит к входу | `G (trying1 -> F crit1)` | **false** |

## Обоснование свойств безопасности

**S2 и S3.** На переходе `idle -> want` процесс поднимает свой флаг. Флаг сохраняется при переходах в `wait` и `crit` и опускается при выходе `crit -> idle`. Шаг другого процесса сохраняет и состояние, и флаг. Поэтому в каждом состоянии с `crit0` поднят `want0` (S2), а в каждом состоянии с `crit1` поднят `want1` (S3).

**S1.** Пусть процесс 0 вошёл первым. По S2 его флаг поднят, поэтому для входа процессу 1 требуется `turn = 1`. Если процесс 1 уже ждал, когда процесс 0 входил, его флаг тоже был поднят и вход процесса 0 требовал `turn = 0`. Если процесс 1 перешёл в ожидание позже, он сам записал `turn = 0` на переходе `want -> wait`. Пока процесс 0 в секции и процесс 1 ждёт, очередь сохраняется. Значит, процесс 1 сможет войти только после выхода процесса 0. Для обратного порядка рассуждение симметрично и использует S3. Вердикты полной проверки всех трёх формул сохранены в `logs/peterson.log`.

## Что считается запросом в L1 и L2

Переход `idle -> want` создаёт запрос на вход. Пока процесс находится в `want` или `wait`, истинно `trying_i`. Начать следующий запрос тот же процесс может только после входа в `crit` и возврата в `idle`. Поэтому в формуле `G (trying_i -> F crit_i)` оператор `G` охватывает каждый запрос, а `F crit_i` требует входа именно этого процесса. Вход по следующему запросу не может скрыть пропуск предыдущего. L1 проверяет процесс 0, L2 — процесс 1.

## Контрпримеры к L1 и L2

В `logs/peterson.log` сохранены контрпримеры BDD-проверки для обеих формул.

Для L1 процесс 0 переходит `idle -> want -> wait`. Затем бесконечно выбирается `run = 1`, процесс 1 остаётся в `idle`, а процесс 0 больше не получает шагов и не входит в секцию.

Для L2 сначала процесс 0 переходит в `want`, затем процесс 1 переходит в `want`. Процесс 0 переходит в `wait` и устанавливает `turn = 1`. Далее бесконечно выбирается `run = 0`: процесс 0 ждёт, поскольку `want1 = TRUE` и очередь принадлежит процессу 1. Процесс 1 остаётся в `want`, поскольку ему не дают шагов. Это петля на состоянии 2.4 трассы.

BMC (`logs/peterson_bmc12.log`) находит более короткие контрпримеры для обеих формул при bound 2. При bound 0 и 1 контрпримеры отсутствуют. Сокращённые трассы:

```
L1:
  pc0=idle, pc1=idle, want0=FALSE, want1=FALSE, turn=0, run=0
  pc0=want, pc1=idle, want0=TRUE,  want1=FALSE, turn=0, run=1
  повтор последнего состояния бесконечно

L2:
  pc0=idle, pc1=idle, want0=FALSE, want1=FALSE, turn=0, run=1
  pc0=idle, pc1=want, want0=FALSE, want1=TRUE,  turn=0, run=0
  повтор последнего состояния бесконечно
```

В каждом случае процесс запросил вход, но навсегда остался вне критической секции. Планировщик модели допускает бесконечный выбор только одного процесса.

## Вывод о свойствах

Три свойства безопасности подтверждены полной BDD-проверкой. Два свойства живости опровергнуты бесконечными траекториями. Таким образом, модель обеспечивает взаимное исключение, а гарантии обслуживания каждого запроса при произвольном планировании нет.

## Эксперименты с опциями

Время и память — `/usr/bin/time`, один прогон на режим, на модели с пятью формулами. Модель крошечная, значения близки к шуму.

| Режим | Результат | Время | Память |
|---|---|---|---|
| BDD (по умолчанию) | как в таблице выше | 0.01 s | 14080 KB |
| BDD, `-coi -dynamic` | те же вердикты | 0.01 s | 13708 KB |
| BMC, `-bmc_length 12` | LTL-свойства: S1 нет контрпримера до bound 12 (это не доказательство, только ограниченная проверка); L1 и L2 ложны, контрпримеры на bound 2 | 0.03 s | 14848 KB |

Выводы: на 40 достижимых состояниях разница режимов не заметна; BMC даёт те же вердикты по L1 и L2, но по безопасности даёт лишь «нет нарушения до длины 12», а полное доказательство даёт только BDD.
